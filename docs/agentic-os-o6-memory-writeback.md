## 0. What the code says today

- **Cockpit owns memory, and only reads it.** `loadMemoryGraph(root)` (cockpit `memory.ts:312`) walks every `*/memory/*.md` under `memory.root` (default `~/.claude/projects`), keeps `mtimeMs`, `project` and `chars` per node, and turns each `MEMORY.md` into an index hub. `gardenFindings` (cockpit `memoryGarden.ts:83`) is pure and returns `orphan`, `ghost`, `stale`, `unindexed`, `duplicate` and `oversized` findings. **`stale` is file mtime older than `staleDays` (default 180)**, severity `info` (`memoryGarden.ts:153`). `GET /api/memory/garden` reconciles finding status into `memory-garden-status.json` only when not `READ_ONLY` (cockpit `server.ts:4447`). The only "fix" path is scheduling a cloud cron job from a finding's prompt (`server.ts:4482`); nothing in Cockpit writes a memory file.
- **No memory bundle exists anywhere.**
  - Plane: memory bundles come only from config, `composer.context.memoryBundles` (`apps/api/src/config.ts:797`). Stage 4 sorts those pins and records them with the evidence `"pinned in config"` (`packages/core/src/composer/context.ts:41`, `:59`). There is no selection by repo, tag or graph proximity, and no health input.
  - Cockpit: `localBundleInputs` answers `memoryBundle: () => undefined` (cockpit `bundleRender.ts:325`), so every pinned memory bundle is `404 not_found` (cockpit PROJECT_MEMORY, M9 section), which the plane maps to `BundleRequestReason "not_found"` (`apps/api/src/modules/bundle-request.ts:30`).
  - Contracts: registry v1 has no memory kind (`contracts/registry/v1/registry-snapshot.schema.json:76`) and names `/memory/bundles` and `/memory/findings` as outside v1 (`docs/contracts/registry-v1.md:34`). Bundle v1 already carries `memoryBundles: [{id, digest}]` pinned by digest and a `memory_bundle` manifest kind (`docs/contracts/bundle-v1.md:25-33`). Spec E proposes the shape `{ id, digest, repoScopes, tags, members: [{path, digest}], estimatedTokens, healthSummary, visibility }`.
  - So the Phase 8 condition has no subject today: there is no bundle to demote. O6 has to define one first.
- **The checkpoint assembler.** `CheckpointService.create` (`apps/api/src/modules/checkpoint.ts:33`) snapshots the envelope, commits the session worktree, records the diff stat and builds `activity_summary` from normalized events (last 3 `message`, 8 `file.changed`, 5 tool calls, tests, 5 errors; `summarizeActivity`, `:150`). A `completion` checkpoint is written by `orchestrator.ts:1102` and `:2137` and by the Harness runner's `attemptCheckpoint("completion")` (`harness/session-runner.ts:935`, `:1647`). `MessagePayload` is `{ text?: string }` (`packages/core/src/events.ts:179`), redacted before persistence like every event.
- **Memory already flows through M6.** The asset usage deriver emits `memory_bundle` rows from `spec.context.memory_bundles` (`packages/core/src/asset-telemetry.ts:202`), the feed is `GET /api/composition/asset-usage` (`telemetry.read`, API 2.7) and Cockpit M10 pulls it (cockpit `assetUsage.ts`, `controlPlane.ts:387`). Once a bundle can render, its attached and outcome facts need no new code.
- **Cockpit's proposals inbox** is dated folders `proposals/<date>/<category>/<name>`, ids `date:category:name`, with plan, accept, reject and edit routes (cockpit `server.ts:4896-5048`). Accept installs into assistant tool roots behind a security gate; `install.ts:37` `ACCEPTABLE_TYPES` has no memory type and no target that resolves to `memory.root`.
- **Profile isolation does not move the Claude config dir.** A composed Claude run launches with `settingSources: ["project"]` (`packages/adapters/src/provisioning.ts:207`) but `CLAUDE_CONFIG_DIR` stays the operator's (`provisioning.ts:704`). Whether a provisioned session can write the operator's `~/.claude/projects/<slug>/memory/` (auto memory, or a plain `Write`) is **not established by the code**. If it can, today's runs already bypass the approval boundary this plan sets. S0 probes it.
- API is 2.7 (`packages/core/src/contracts.ts:28`). Migrations run to `037`; `038` is reserved for M6 S4's shadow log. `graphify-out/graph.json` is not in either checkout, so this plan was read from source.

## 1. Vocabulary

- **memory file**: one `.md` under a `memory/` directory, one fact, with frontmatter. Cockpit's.
- **memory bundle**: a named, operator-declared set of memory files Cockpit can render, with a digest over its members. Cockpit's.
- **health**: Garden findings whose nodes are members of a bundle, summarized per bundle.
- **demotion (shadow)**: the plane's record that, by the health rule, it *would* drop or rank down a bundle. It never changes what the run gets.
- **proposal**: a candidate memory write the plane extracted from a finished run. The plane stores it and publishes it; it is never a write.
- **acceptance**: the operator, in Cockpit, turning one proposal into a memory file. The only write path.

## 2. Design

### 2.1 Memory bundles (Cockpit owns, Q1)

- Declared in Cockpit config: `memory.bundles: [{ id, dir, tags, repoScopes, visibility }]`, `dir` relative to `memory.root` and resolved through the existing path guards (no `..`, no symlink escape). `id` matches the bundle v1 pattern `^[A-Za-z0-9][A-Za-z0-9._:-]{0,127}$`.
- Members: the `.md` files directly in that `memory/` dir, `MEMORY.md` included, sorted by path. Member digest = sha256 of raw bytes (the fragment rule, ai-control-plan #84). Bundle digest = the registry asset digest over the member list, so the same algorithm and fixtures cover it.
- Render: `localBundleInputs.memoryBundle(id)` resolves the declared bundle, recomputes its digest and renders members in path order. Bundle v1 is unchanged: a pin whose digest moved is still `404`, and the next compose picks up the new digest from the snapshot. No versioned memory store (spec E).
- **Health** per bundle, computed by Cockpit from `gardenFindings` over the same graph: `{ members, staleMembers, oldestAgeDays, duplicatePairs, ghosts, oversized, findingsDigest }`. Age uses the frontmatter `metadata.modified` when present and file mtime otherwise, because a git checkout or a sync resets mtimes (§7).

### 2.2 The read path: stale bundles demoted in shadow

- **Federation.** The plane syncs `GET /api/v1/registry/memory/bundles` beside the registry snapshot (boot and the daily job), with the same token, validation, last-good cache, `observedAt` and `stale` flag as M4 (`registry-federation.ts`).
- **Production is unchanged.** Stage 4 still renders exactly `composer.context.memoryBundles`. Nothing about health enters the decision, the spec, `compositionDigest` or `inputs_digest`; if it did, a health change between preview and start would fire `composition_drift` (the trap M6 §4.2 names).
- **Shadow rule** `memory-shadow/v1`, a pure core function with no clock (the snapshot's `observedAt` is the time): for each pinned bundle, `demote` when `staleMembers / members ≥ 0.5`, else `keep` (Q3). A bundle missing from the snapshot is `unknown`, a digest that differs from the pin is `drifted`. The reason text names the counts and the oldest age, e.g. `stale: 4 of 7 members, oldest 214d`.
- **Shadow log.** One row per composition attempt that reached stage 4, per pinned bundle: `attempt_id`, `bundle_id`, pinned digest, snapshot digest, production action (`included` / `excluded_by_renderer` / `not_found`), shadow action, reason, `findings_digest`, scorer version. Written after the attempt row and outside its transaction, best-effort; a scorer error writes a row with the error and never fails a compose (M6 S4's pattern).
- **Visible.** `GET /api/composition/memory-shadow?taskId=` (`telemetry.read`) and a chip on the memory row of the web Composition panel (`apps/web/src/Composition.tsx:142`): "shadow: would demote, stale 4 of 7, oldest 214d". That is the Phase 8 condition: visibly demoted, production selection untouched. Activation is a later slice with a K13-style gate; O6 ships none.

### 2.3 The write path: proposals at checkpoint, accepted in Cockpit

- **When (Q4).** At a `completion` checkpoint of a session that has a composition revision and ends `success` by `reliabilityClass`. Not on `handoff`, `limit`, `cancel` or `context`: those runs did not finish, and a gotcha from a failed run is better found by the operator than proposed.
- **Where the content comes from (Q2).** The agent, not a second model call. An operator-configured fragment (for example `memory-proposal-protocol`, rendered through bundle v1 like any fragment) asks the agent to end with one fenced block, ` ```agent-plane-memory `, holding a JSON array of at most 5 `{ kind: decision | gotcha | fact, name, description, body, targetBundle?, supersedes? }`. The plane parses it deterministically from the session's last `message` event text. No block, no proposals; a malformed block is counted and dropped. No transcript is read beyond that one message.
- **What a proposal carries.** `proposalId` = `"mp1_" + hex sha256(JCS({v:1, sessionId, index, bodyDigest}))`; `sessionId`, `taskId`, `compositionRevisionId`, `checkpointId`, `harness`, resolved `model`; `kind`, `name` (kebab slug), `description` (one line), `body` (≤ 4 KB, the memory file limit); `target { bundleId, bundleDigest }` only if it names a bundle the revision pinned, else `null`; `supersedes` (member file names in that bundle); `evidence { outcome, verificationPassed, changedFiles }` (counts only); `at` = the checkpoint's `at`, never the clock.
- **Guards before storing.** The plane's redaction plus the bundle content guards (inline credential, absolute path, hostname, timestamp-shaped secret). A proposal that trips one is **dropped with a counted reason, never redacted**, because a redacted memory is a wrong memory. Test values are `FAKE-*-not-real`.
- **Storage and feed.** An append-only `memory_proposals` table (next free migration number, `039` if M6 S4 has taken `038`; UPDATE/DELETE refusal triggers; `INSERT … ON CONFLICT DO NOTHING` then compare body digest, as in M6 §2.2). Feed `GET /api/memory/proposals?after=<seq>&limit=<≤100>` behind a new `memory.read` capability (Q5), API 2.8. The plane has no route that accepts, rejects or writes memory.
- **Cockpit pulls.** Same poller shape as M10 (`assetUsage.ts`): off unless `memoryProposals.enabled`, `CONTROL_PLANE_URL` and `CONTROL_PLANE_CREDENTIAL_PATH` are set, never under `READ_ONLY`. Each event becomes `proposals/<date>/memory/<name>.md` (frontmatter in the memory format plus a provenance block: task, session, revision, model, outcome), deduped by `proposalId`; a second body under a known id is set aside as a conflict and the first stays.
- **Approval boundary.** Only `POST /api/proposals/:id/accept` on a `memory` proposal writes, and only after the operator presses it in the loopback UI. It writes into the target bundle's `memory/` dir (or a dir the operator picks; never a caller-supplied path) with Cockpit's atomic write, backs up any file it replaces or a `supersedes` member it edits via `backupToTrash`, and adds the `MEMORY.md` pointer line. Reject keeps the record and writes nothing. No auto-accept: memory proposals are never `eligibleForAutoFix`. The plane learns of an acceptance only through the next bundle snapshot, whose digest moves.

## 3. Contract changes (land here first; Cockpit vendors SHA-pinned)

- New `contracts/memory/v1/`: `memory-bundle-snapshot.schema.json` (Cockpit serves, plane consumes: `{ schemaVersion, snapshotDigest, observedAt, bundles: [{ id, digest, tags, repoScopes, visibility, members: [{ path, digest }], estimatedTokens, health }] }`, closed objects, sorted, `path` relative with no `..`), `memory-proposal-event.schema.json` and the feed page (plane serves, Cockpit consumes), fixtures valid and invalid, `docs/contracts/memory-v1.md`, reference validator `apps/api/src/memory-contract.ts`.
- `memory.read` capability and `CONTROL_PLANE_API_VERSION` 2.8 in `packages/core/src/contracts.ts`. Cockpit's credential then needs a rotate with `--capabilities`.
- Registry v1 and bundle v1 are unchanged. `registry-v1.md:34` gets one line pointing `/memory/bundles` at memory v1; `/memory/findings` stays out (health travels inside the snapshot).
- Cockpit vendors `contracts/memory/v1` into `contracts/memory/` with `VENDORED.json` and the sha256 manifest test, as for registry, bundle and asset-usage.

## 4. What this plan does not do

- No production demotion, no ranking of bundles by health, no auto-selection by repo or tag (§3.6's read path beyond shadow is Phase 10 / O7 territory).
- No LLM summarizer over transcripts, and no proposal from a failed or unfinished run.
- No plane write to any memory file, and no Cockpit write without an operator press.
- No vector index (O7).

## 6. Questions for itay (my default in bold)

- **Q1** A memory bundle is an operator-declared entry in Cockpit config (`memory.bundles`), not one bundle per memory project dir found on disk? **Declared.** Auto-discovery would expose every project's memory to composition by default; spec E's `visibility` needs an owner.
- **Q2** Proposals come from a fenced block the agent writes at the end of a successful run, asked for by a configured fragment, and parsed without a second model call? **Yes.** It costs no quota, is deterministic, and keeps the plane out of transcript summarizing. An LLM summarizer can come later as an opt-in slice.
- **Q3** Shadow rule: demote when at least half a bundle's members are stale by the Garden's `staleDays` (180), with age from frontmatter `modified` before mtime; duplicates and ghosts shown but not demoting? **Yes.**
- **Q4** Proposals only at `completion` checkpoints of composed sessions that ended `success`? **Yes.**
- **Q5** A new `memory.read` capability (API 2.8) for the proposal feed, rather than reusing `telemetry.read`? **New.** Proposal bodies are memory content, not counts, so a telemetry-only credential should not read them. Cockpit's credential is rotated once with `--capabilities`.

## 7. Findings from reading the code

- Cockpit renders no memory bundle (`bundleRender.ts:325`), so any `composer.context.memoryBundles` pin fails its bundle request with `not_found` today. The Phase 8 condition cannot be shown until S2.
- Garden `stale` reads file mtime. A `git checkout`, a sync job or a restore resets it, so synced memory under-reports staleness. S2 prefers frontmatter `metadata.modified`, which the project's memory files already carry.
- `CLAUDE_CONFIG_DIR` is not isolated for composed runs (`provisioning.ts:704`). Whether that lets a run write operator memory is unknown; S0 settles it before any write path ships.
- Plan §3.6 says "same accept/reject UX as trends proposals", but the accept path installs into assistant tool roots and has no memory target (`install.ts:37`). S6 adds one.
- Spec E lists `GET /api/v1/registry/memory/findings`; this plan folds health into the bundle snapshot instead, so the plane makes one call and the snapshot digest covers the health it saw.
- `graphify-out/graph.json`, which both AGENTS.md files say to query first, does not exist in either checkout.

**Verdict: SKIP** (plan only, no runtime surface).
