# Codex correlated receipts: durable identity, no deduplication

2026-09-23. The SDK-pinned **Codex CLI/app-server 0.154.0** accepts
`turn/steer.clientUserMessageId` and persists that exact value as
`userMessage.clientId`. A new app-server process can read it after the execution
owner exits or is killed. The separate provider-generated `userMessage.id` also
survived the measured restarts. Repeated caller IDs were **accepted twice**.

This supports receipt lookup, not idempotent send or provider consumption.
The existing accepted transport adapter at `4c0c6bd` is unchanged on its branch.
The implementation in this research branch introduces capability version
`codex-app-server-receipt-v2` only after the matrix below established correlation.

The runner resolves the same SDK-owned binary as the execution runtime; it

already exposes the caller field in **0.154.0**; it is not exclusive to the
newer PATH version mentioned in the earlier transport report.

The [official protocol documentation](https://learn.chatgpt.com/docs/app-server)
describes steering an active turn with `expectedTurnId`. The durable correlation
and duplicate conclusions here come from the pinned executable's actual
requests and fresh-process history, not from current online documentation.

Recorded artifacts contain field names, booleans, statuses and counts. They
contain no request text, assistant output, actual caller/thread/item IDs,
credentials, provider diagnostics or raw transcripts. Input fixtures stay
outside the repository. Text matching exists only in the measurement runner to
count synthetic input occurrences; the adapter never uses text matching.

## Manual matrix

Every successful steer response contained only `turnId`; it did not itself
provide a message receipt. Requests used `threadId`, `expectedTurnId`, `input`
and `clientUserMessageId`, except the explicit no-caller-ID control. Text input
fields were `type` and `text`. History was read with `thread/read` using
`threadId` and `includeTurns`; the response contained `thread` and the user item
fields `type`, `id`, `clientId`, `content`.

| Case | Fresh process finds exact caller ID | Stored input occurrences | Result |
|---|---|---:|---|
| Unique ID and unique text | Yes | 1 | Durable correlation |
| Identical text, two different caller IDs | Yes, each independently | 2 total, 1 per caller | Text is not used as identity |
| Same caller ID twice, concurrent in one live turn | Yes | 2 | Both requests accepted |
| Same caller ID again after first RPC response | Yes | 2 | No deduplication |
| Same caller ID after disconnect/reconnect | Yes | 2 | No deduplication |
| Same caller ID after completed model response, next live turn | Yes | 2 | No deduplication |
| Same caller ID after provider restart, next live turn | Yes | 2 | No durable deduplication |
| Disconnect before observing steer response | Yes in first run; absent in repeat | 1 / 0 | Delivery races disconnect; absence remains unresolved |
| Disconnect after provider success, before caller gets response | Yes | 1 | Transport response deliberately withheld |
| Completed turn | Yes | 1 for unique input | Terminal completion preserves record |
| Interrupt immediately after steer success, before fold | No | 0 | Success was only queue/transport acceptance |
| Interrupt after correlated user item is emitted | Yes | 1 | Already-recorded correlation survives interruption |
| Wrong `expectedTurnId` during active turn | No | 0 | Rejected; no input effect |
| Provider item ID without caller-ID field | No | 1 | Generated ID alone does not correlate the ledger |
| Kill provider after steer success, before caller gets response/fold | No | 0 | An acknowledged queued input can be lost |
| Runtime's stdio transport, unique caller ID | Yes | 1 | Fresh stdio reader confirms the same contract |

The counts describe stored synthetic user-input occurrences, not external
side effects or exactly-once tool execution. In the JSON,
`duplicateEffectCount` counts occurrences of that case's synthetic text;
`callerCorrelatedItemCount` distinguishes the two logical IDs in the identical
text case, and `distinctClientIdCount` distinguishes repeated IDs from distinct
IDs. Provider-generated item IDs were present and distinct from caller IDs for
recorded inputs; their stability is checked separately across restart.

Connection-loss tests use loopback WebSocket transport so a caller can
reconnect without killing the provider. The pre-response boundary closes the
client immediately after enqueueing its request, before resolving a response.
The post-response boundary observes the real provider's result inside the
transport, withholds it from the request promise, and closes the connection.
The pre-response disconnect stored one input in the first matrix and none in
the repeat; a socket close can prevent acceptance, so this case has no
deterministic delivery outcome. The crash boundary additionally uses `SIGKILL`. Fresh readers are independent
provider processes, not caches of notifications. Reconnect explicitly resumes
the existing thread on the same provider process to restore subscriptions.
The first harness attempt omitted that subscription and timed out; it was
corrected before the two complete matrices and supports no receipt conclusion.

These observations are bounded to the pinned version/platform and the measured
boundaries. They do not prove durability through disk loss, arbitrary history
retention/compaction, all versions, or all transports. A failed or absent later
read remains unresolved; it is never interpreted as proof of non-delivery.

## Minimal adapter change and acknowledgement rule

`CodexSessionInputAdapter` passes the ledger's logical `messageId` unchanged in
`clientUserMessageId`. The send still uses the execution owner's existing active
thread and expected turn. The default-off workspace flag, assistant transport
opt-in, session grant, identity checks and local duplicate guard are retained.

A matching steer response has only transport significance. `deliver` therefore
raises `SessionInputUnresolvedError("transport_ack_only")`, keeping the ledger
`accepted` and unknown. It cannot return a transport receipt under the new
provider-accepted capability: the existing service treats returned receipts at
the declared capability level. This preserves that contract without changing
shared types or service code, and prevents a response from being upgraded by
capability declaration alone.

`lookupReceipt` starts a new SDK-pinned app-server, initializes it and calls only
`thread/read` with turns included. It checks the provider thread identity, then
requires a `userMessage` whose `clientId` exactly equals the ledger message ID,
with a provider item ID and content array. The provider-authored stored record
proves that the provider recorded this logical input, satisfying
**provider-accepted**. It does not prove assistant consumption.

The receipt references the provider thread and item IDs. Its `at` is the
observation time, not an invented provider timestamp. The reader never resumes
a writer, starts a turn, steers a turn, or reads a raw rollout itself. It drains
private diagnostics, masks read failures, and terminates its child with bounded
cleanup. An execution binary override is also used by that owner's reader.

The v2 declaration is `receiptLookup:true`, `idempotentSend:false`,
`ackLevel:"provider-accepted"`. Every receipt actually returned is supported by
the fresh durable record. The transport response itself is never a receipt at
that level; forged ack fields in a JSON-RPC response are ignored.

A missing, malformed, mismatched or unreadable record throws unresolved.
**Lookup never returns `null`.** The service therefore cannot take its
null-lookup replay path. Lookup also works without a live owner or a renewed
session grant: revoking sends must not erase evidence of prior delivery.
Historical transport-v1 attempts have no sent caller ID and remain unresolved;
this change neither infers their identity from text nor migrates their claims.

## Reproduction and validation

Both manual runners require explicit opt-in and an external JSON fixture with
`initial` and `followup` string properties. Use synthetic text only: the initial
instruction should perform one bounded shell sleep, leaving a live steer window,
then complete without other tools, network, delegation or file modifications.
No prompt fixture belongs in the repository.

```sh
LIVE_CODEX_CORRELATION=1 \
SPIKE_INPUT_PATH=/absolute/private/fixture.json \
SPIKE_REPORT_PATH=/tmp/codex-correlation.json \
pnpm --filter @agent-plane/api exec tsx \
  ../../packages/adapters/spikes/codex-correlated-receipts.mjs

LIVE_CODEX_CORRELATION=1 \
SPIKE_INPUT_PATH=/absolute/private/fixture.json \
SPIKE_REPORT_PATH=/tmp/codex-receipt-ledger.json \
pnpm --filter @agent-plane/api exec tsx \
  ../../packages/adapters/spikes/codex-correlated-receipt-ledger.mjs
```

The first runner exercises the real protocol matrix. The second uses the actual
execution adapter, HTTP API, SQLite ledger and fresh reader, with scripted
kernel session registration. It closes/reopens the plane database while the
provider runs and reconciles after provider exit. The old transport-only manual
runner is a historical v1 probe for commit `4c0c6bd`, not the v2 validation entry.

The live ledger runner passed with two identical-text logical messages: two
original sends, both initially unknown, database close/reopen, observed execution
owner process exit, a fresh adapter with no grant, two distinct provider receipts,
one stored user item and one ledger attempt per logical message, and **zero
recovery sends or live-owner connection lookups**. The exit witness uses Linux
procfs to identify the exact SDK binary child and observes that PID exit before
recovery. This measured platform was Linux arm64.

Deterministic coverage additionally checks duplicate text with only one logical
message actually stored, later visibility, absent/failed/malformed/mismatched
history, provider IDs without caller correlation, assistant output, forged
response acknowledgements, revocation, default-off routes and restart without
resend. Reader tests prove a fresh process per read, only initialize/read RPCs,
fixed failure diagnostics and bounded cleanup. No shared interface was changed.

Final lint, typecheck, build and all package suites passed: core **118**,
adapters **60**, API **970**, web **57** (**1,205** tests). Forced-harness
(single mode on) passed **970**, recovery chaos passed **56**, and Chromium
passed **32**. Secret scans of staged, unstaged, last-commit and complete-slice
additions were clean; only documented Git hashes matched the generic token
pattern. Generated screenshots were restored; there is no UI change.
The final test setup failure was corrected before this full passing run; it did
not require weakening an assertion or changing provider behavior.
