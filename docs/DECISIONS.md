# Decisions

- Route complete assistant environments, not bare models. Supported by README and adapter contracts.
- Start with deterministic eligibility and explainable preference routing; telemetry informs later selection. Supported by architecture review and implementation.
- Isolate personal/work data using separate control-plane processes and workspace directories. Supported by configuration and isolation tests.
- Keep provider credentials outside the plane database/configuration. Supported by revised architecture and adapter authentication probes.
- Use normalized events and portable checkpoints as the handoff boundary. Supported by core contracts and orchestration implementation.
- Use SQLite for the local-first prototype. Supported by API dependencies and migrations.
- Remote runners and broader Agentic OS services remain proposals, not accepted implementation commitments.
- Maintain this as a documentation worktree of the control plane, proven by Git worktree metadata and common history.
- Treat the Agentic OS lifecycle/contracts as proposed until merged and implemented.
- Preserve the existing control-plane adapter/event/checkpoint boundaries as the base of any wider platform.
- No evidence supports an independent deployment or product identity for this worktree.
- Kernel services (2026-09-05, `docs/agentic-os-kernel-services.md` revision 2): the task machine gains exactly one state, `WAITING_RESOURCE`, meaning the scheduler owns a parked task with no live or ambiguous execution owner; outcomes never become states (CR-16). Deferral never bypasses an approval, verification or comparison decision (CR-32). A parked task stores durable user intent and wait subjects only; execution choices are recomputed at every dispatch, anchored to an explicit checkpoint or explicitly fresh, and recorded as a new routing decision (I-S1). Dispatch identity is durable before any provider call; at most one live owner per task; exactly-once provider execution is not claimed (I-S3).
- A retry timestamp (`CooldownStore.until`) is not evidence of quota recovery; every blocker carries kind, source, observation time, scope and reset provenance, one effective quota projection serves router and scheduler, and a wake revalidates before it starts (I-S4, CR-29). Idle quota probes are optional, account-scoped observations, never a manifest capability (CR-22).
- One routing entry point for intake, wake, failover and context yield (CR-30); fresh-vs-resume is an explicit continuation decision, not a trigger label (CR-31).
- Model-level selection is kernel scope (M12) in two steps: execution identity first (requested selector and resolved identity recorded separately, `unknown` allowed, one authority for `ExecutionRequest.model` — CR-33, I-M5), then shadow selection with hard filters no benchmark can bypass and gated activation. The earlier "deferred indefinitely" entry is withdrawn. Published benchmark scores are cold-start priors weighted `1 − n/(n+k)`; own telemetry's weight is monotone in `n` and can never be switched off (CR-17, I-M2). Running synthetic benchmarks stays rejected. K7 supplies versioned price evidence; bounded cost caps stay deferred behind five gates and are never authorized by benchmark prices or Cockpit's family-match fallback.
- Context management is observation first: occupancy, effective window, advertised maximum, source and freshness are shown (unknown allowed) before anything acts; continuation is checkpoint-anchored, evidence-adequate, bounded per task and not lossless; provider auto-management is primary and provider compaction is a capability-gated mechanism, not the architecture (CR-34). It never clears a session, never mutates persisted history, and never continues automatically on unknown or stale observations (I-C1, I-C2, I-C3).
- M15 runtime enum and abstraction deferred; `SessionRunner.startProvider` is the seam; no `RuntimeBackend` interface before its second implementation; herdr and DeepSeek Harness are optional on demonstrated need, never dependencies (CR-28). `jobs.ts` consolidation deferred (CR-24).
- The Control Plane owns price evidence (model catalog, `pricingVersion`) and schedules; Cockpit renders both, keeps an offline catalog snapshot, and creates schedules only through `commands.write` (CR-19, CR-20).
